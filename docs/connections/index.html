How a system gets connected

Four ways in. Every tool you run is one of them.

What matters for planning isn’t the logo — it’s which of these four a system falls into. That decides how long it takes, how sturdy it is, and what it costs to keep running.

The case How we connect it Typical examples Time to working
A connector already exists Install the vendor’s or the open MCP connector, provision a service account, scope it per role. Gmail, Google Drive, Slack, Notion, HubSpot, Asana Same week
There’s an API but no connector We build the connector against the vendor’s API — auth, pagination, rate limits, retries, the lot. Your billing platform, your scheduling tool, the vertical software your industry runs on One to two weeks
You built the tool yourself We wrap your internal service so your AI calls it like any other tool. Your engineers keep owning the service. Internal dashboards, ops consoles, proprietary tooling One to two weeks
There is no API at all We drive a real signed-in browser session through the same screens your team uses, and expose that as a tool. Legacy vendor portals, carrier and government sites, older industry software Two weeks, then monitored

The fourth row is the honest one. Browser-driven connections work, and they’re the most fragile thing we build — a vendor redesign breaks them. So they’re monitored, and they fail loudly rather than quietly returning something wrong.

Inside one connection

A connection is not an API key in a config file.

Between the model asking for something and your billing system doing it, there are three checks. Every one of them is there so that call can’t do something you didn’t intend.

The model asks
→

→

→

Normalized result back

The same five stages sit behind every connection in the catalog, whether it took an afternoon or a fortnight to build.

Auth is the hard part, not the API

Connections run on service accounts your IT provisions, never on a person’s borrowed login. Tokens refresh on a schedule, rotate without downtime, and revoke in one place. When someone leaves, nothing silently breaks — and nothing silently keeps working.

Scoped per role, not per company

The support role reads payroll and cannot write to it. Sales can send from the shared mailbox and cannot touch the ledger. One connection, different reach depending on who is calling it.

Rate limits, respected

Every vendor throttles differently, and the fastest way to get an integration switched off is to hammer it. Calls back off, queue and retry rather than pile up.

Writes are idempotent

Every write carries an idempotency key, so a retry after a dropped connection can’t double-charge a customer or send the same email twice — the failure that costs the most trust for the least reason.

Every call is logged

Which role called it, which rule let it through, what came back. That’s what makes an AI decision reviewable a month later instead of a thing that just happened.

Hosted where you need it

Inside your VPC if your security team requires it, on our infrastructure if you’d rather not think about it. That changes where the credentials sit, not what the connection does.

When nothing off the shelf exists

The connector we build for the tool only you use.

This is the part most teams give up on, and it’s usually the system the work actually lives in. Here is what building one looks like.

Step 1

Find out what it can actually do

Read whatever documentation exists, then test it — what the endpoints really return, where the pagination lies to you, what the throttle is before the vendor says so. Half of this work is finding the gap between the docs and the behaviour.

Step 2

Get the credentials right

A service account your IT provisions, scoped to the least it needs, with refresh and revocation working before anything is built on top. Auth is where these projects die, so it goes first, not last.

Step 3

Wrap it as a tool, not as an endpoint

The model shouldn’t see a REST API. It sees a named tool with a clear job, validated inputs and a normalized result — so a skill written against it keeps working when the vendor changes their response shape.

Step 4

Make the failures boring

Retries with backoff, idempotency keys on every write, and a loud, specific error when the vendor is down. A connection that returns something plausible while it’s broken is worse than one that stops.

Step 5

Hand it over

It ships into your operational layer with the rest of them, version-controlled and documented. Your team can read it, change it and run it without us.

What we need from you

Three things, and none of them are engineering hours.

Connecting your systems is our work, not a project we hand back to your team. What we do need is short.

  • A name per system — whoever administers it and can approve a service account
  • A scope decision — what each role may read, what it may write, and what needs a signature first
  • An hour with whoever uses it daily — because the documented workflow and the real one are rarely the same

Then it’s ours until it works, and yours to keep afterwards.
